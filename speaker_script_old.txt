## SLIDE 3 — Project Overview
**SPEAKER A**

The objective of this case study was to design and implement a database for a fitness center. We were given a set of wireframe screens and had to identify the entities, attributes, and relationships from those screens. The result is a database with 14 tables, all in Third Normal Form. We mapped queries to 4 wireframe screens, created 2 MongoDB collections, and completed all 6 deliverables.

## SLIDE 4 — Conceptual EER Diagram
**SPEAKER B**

This is our Conceptual EER Diagram, built using Draw.io. We identified 8 strong entities: Member, Coach, Location, Class, Amenity, Certificate, and two more. We also identified 2 weak entities: Review and Reference. Review is weak because it depends on both a Coach and a Member. Reference is weak because it belongs to a Coach.

The association tables you see here, like Member_Coach, Location_Coach, and Class_Enrollment, resolve the many-to-many relationships between entities. Each entity's primary key is underlined, and derived attributes like avgRating are marked with a DA label.

## SLIDE 5 — Relational Model (3NF)
**SPEAKER A**

This is the Relational Model, which we derived from the EER diagram. We converted every entity and relationship into a table. The result is 14 tables total, listed at the bottom right.

To verify Third Normal Form, we checked three conditions. First normal form: all attributes are atomic with no repeating groups. Second normal form: every non-key attribute depends on the complete primary key. Third normal form: there are no transitive dependencies. Every attribute depends only on the primary key, not on another non-key attribute.

The association tables use composite primary keys. For example, Member_Coach uses memberID and coachID together as the PK. The derived attributes avgRating and overallRating are calculated values, but we kept them in the table for query performance.

## SLIDE 6 — SQL: CREATE TABLE Scripts
**SPEAKER B**

Here you can see samples of our CREATE TABLE scripts. On the left we have the Member and Coach tables. On the right we have the Location table and an example of an association table, Location_Coach.

Every table enforces its primary key. Tables that reference other tables use FOREIGN KEY constraints. For example, Location_Coach has two foreign keys, one pointing to Location and one pointing to Coach. This enforces referential integrity across the database. The same pattern applies to all 14 tables.

## SLIDE 8 — MongoDB Collections
**SPEAKER B**

For Deliverable 5, we converted two entities to MongoDB collections: Locations and Coaches. You can see the scripts on the left. We use the fitness_center database, create each collection, and insert a document.

The key difference from SQL is that MongoDB allows embedded arrays. For Locations, the amenities are stored directly inside the document as an array. For Coaches, we embed certificates and references as nested objects. This is why MongoDB is a good fit here. In SQL, amenities require a separate junction table. In MongoDB, everything for one location lives in one document. This is what we mean by polyglot persistence: using the right tool for each type of data.

---

## SLIDE 9 — SQL SELECT Statements
**SPEAKER A**

For Deliverable 6, we wrote SELECT statements to return the data shown in each of the four wireframes.

Wireframe 1 returns the locations a member has visited this month, with visit counts. It uses a JOIN between Member_Visit and Location, filters by memberID and the current month using strftime, and groups by location.

Wireframe 2 returns the details for the Midtown Studio location, including its amenities and coaches. We use two separate queries: one for the location details and one that joins through the Location_Amenity association table.

Wireframe 3 returns the coaches. The first query shows only the coaches assigned to the logged-in member. The second returns all coaches in the system.

Wireframe 4 returns a full coach profile, including their name, level, rating, training philosophy, certificates, and references. Each piece comes from a separate query joined through the Coach_Certificate table.
